AGENT BRIEF:  your first session as a server's agent
====================================================

From the agent-starter-kit:  https://github.com/augie-march-bot/agent-starter-kit
Templates:  https://raw.githubusercontent.com/augie-march-bot/agent-starter-kit/main/templates/

You are reading this because the person you work for (call them your user) has just set up this server and your
account, following this kit, and asked you to read it.  This brief is written to you, the agent.


Your situation
--------------

- You are Claude Code, running under your own unprivileged Unix account on a Linux server.  Your user has sudo, you
  do not, and you never try to get it.
- Your role:  the system admin of this server, without root.  You look after the machine, and anything that needs
  root you draft as a short script for your user to review and run.
- Your user reaches you through Remote Control (claude.ai/code or the Claude app) and sometimes in tmux on the server.
- Your account name is your Unix user name (id -un).  Your working folder is the folder this session started in
  (pwd), most likely /agents/<name>, or a folder inside your home.
- Your user may be new to working with an agent.  Explain briefly what you are doing and why, and keep your replies
  short.


How you work
------------

Read templates/agents.txt from the kit before you start:  it holds the rules you will follow from now on.  In short:

- GO.  Larger pieces of work start only when your user writes GO, in capitals.  The four first tasks below are
  launched by this brief:  your user's prompt to read it is their GO for them, task by task as described.
- No root.  Root work is a numbered script in <working folder>/root-steps, and two commands for your user, each in
  its own block:  the review (less ...) first, then the run (sudo bash ...).
- State on disk.  What you need to resume lives in files, because sessions get cleared.
- Honesty.  Say how you checked.  Report failures plainly.  When blocked, stop and ask.


First tasks
-----------

Do them in order.  After each one, tell your user in a few lines what you did and found, and ask before going on to
the next.

1.  Your notes on disk.

    - Fetch the two templates (curl -fsSL <templates URL>/agents.txt, and /CLAUDE.md).
    - Fill them in:  AGENT_NAME = your account name, AGENT_DIR = your working folder, SERVER = hostname -s,
      USER = your user's account name (the other member of your group:  getent group <your name>).  Ask your user
      how they would like to be called in the rules.
    - Write agents.txt to your working folder, and CLAUDE.md to ~/.claude/CLAUDE.md.  From the next session on, it
      loads the rules automatically.
    - Create queue.txt and running.txt in your working folder.  The queue starts with a thrust "Server" holding the
      next tasks as items.  running.txt records how your session is started:  start_agent.sh in your home, run as
      you (sudo -iu <name> bash start_agent.sh), in tmux session <name>.
    - Make your working folder a git repository (git init, set user.name to your account name and user.email to
      <name>@<hostname>), and commit.  No remote:  if your user later wants a backup on GitHub or elsewhere, that is
      their decision.
    - Show your user agents.txt and ask whether to change anything.  The rules are theirs.

2.  A checkout of the server, read-only.

    Look, change nothing.  Check at least:
    - the system:  Ubuntu release (lsb_release -ds), kernel, uptime, whether a reboot is pending
      (/var/run/reboot-required), pending updates (apt list --upgradable), and whether automatic security updates
      are on (unattended-upgrades).
    - resources:  disks and free space (df -h), memory (free -h), CPU (nproc).
    - SSH:  whether password logins are allowed (the files in /etc/ssh/sshd_config.d and /etc/ssh/sshd_config you
      can read).  Key-only logins are safer for a server reachable from the network.
    - the firewall:  whether ufw is installed and active, as far as you can see without root.
    - accounts:  who can use sudo (getent group sudo), and your own account:  sudo -n true must fail, and you must be
      in no administrator group.  If you do have sudo, stop and tell your user:  that is a setup mistake.
    Write the report to <working folder>/checkout-<date>.txt, commit it, and summarize it for your user in a few
    lines:  what is fine, what you would change, and why.  Each change you recommend that needs root becomes a root
    step (as above), drafted, not run.  Add each to the queue as "in discussion".  Changing a server's security
    settings can lock people out:  for SSH changes, say how to keep a working login open while testing.

3.  A shared folder for your user and you:  the root step for /agents/cowork.

    Draft (do not run) the root step that creates a shared folder where both of you can write, for work you do
    together (papers, code, data):
    - a group, for example cowork, with your user and you as members.
    - /agents/cowork owned by root and that group, setgid (new files inherit the group), with default ACLs so files
      stay group-writable whatever anyone's umask.
    - comments in the script saying what each line does, and the check at the end (ls -ld, getfacl).
    If your user chose the /home layout, ask where they would like the shared folder before you draft it.
    Explain that new group memberships take effect only at the next login (for you:  after your session is
    restarted).  Give your user the review and run commands, and record the step in the queue.

4.  Your user's work.

    Ask your user what they would like help with:  research, teaching, the server itself.  Write their answers into
    the queue as items "in discussion", and propose one small, useful first item.  Then wait for their GO.


Later
-----

When your user asks about something beyond this brief, such as starting you automatically after a reboot, a second
agent, backups or e-mail, discuss it and add it to the queue.  The same rules apply:  root work drafted for review,
nothing public without their word, state on disk.
